BENCH TEST PROCEDURES (Hardware Required)
================================================================================

Phase 1: Component Validation (15-20 min)
  └─ Verify all 5 sensors responsive and healthy

Phase 2: State Transitions (5 min)
  └─ Test STARTUP → ... → LANDED state sequence

Phase 3: Apogee Detection (20 min)
  └─ Test 5 consecutive barometer descent readings trigger apogee

Phase 4: Landing Detection (15 min)
  └─ Test robust landing detection with wind gust simulation

Phase 5: Guidance System (30 min if enabled)
  └─ Test PID controller and servo outputs

Phase 6: Data Logging (10 min)
  └─ Verify SD card logging and CSV format

Phase 7: Command Processor (15 min)
  └─ Test all serial commands execute correctly

Total Bench Testing: ~2 hours per complete cycle

================================================================================
HARDWARE ABSTRACTION LAYER (HAL) DESIGN
================================================================================

Three-Layer Architecture:

Layer 1: Interfaces (C++ pure virtual classes)
  ├─ hal_i2c.h (I2C operations)
  ├─ hal_timer.h (millis/micros)
  ├─ hal_gpio.h (digital I/O)
  └─ hal_serial.h (UART communication)

Layer 2: Implementations (swappable)
  ├─ hal_i2c_teensy.cpp (real Teensy Wire library)
  ├─ hal_i2c_mock.cpp (mock for testing)
  ├─ hal_timer_teensy.cpp (real millis)
  ├─ hal_timer_mock.cpp (simulated time)
  ├─ hal_gpio_teensy.cpp (real GPIO)
  └─ hal_gpio_mock.cpp (mock GPIO)

Layer 3: Business Logic (unchanged external API)
  ├─ flight_logic.cpp (uses HAL)
  ├─ sensor drivers (use HAL)
  ├─ guidance_control.cpp (uses HAL)
  └─ state_management.cpp (uses HAL)

Benefits:
  ✓ Test without hardware
  ✓ Inject test data (simulated flights)
  ✓ Deterministic execution (no real-time jitter)
  ✓ Backward compatible (existing code unchanged)

Effort: ~1100 lines of new code, 10-12 weeks to fully implement

================================================================================
RISK MITIGATION
================================================================================

Top Risks & Mitigations:

Risk: Testing finds bugs close to flight date
  → Mitigation: Start testing immediately, parallel bench work

Risk: Refactoring introduces regressions
  → Mitigation: All existing hardware tests must pass, incremental refactoring

Risk: Test coverage metrics don't reflect actual code quality
  → Mitigation: Use line + branch + path coverage, code review

Risk: Sensor mocks too simplistic, miss real behavior
  → Mitigation: Validate mocks against real flight data post-flight

Risk: CI/CD false failures slow down development
  → Mitigation: Quarantine flaky tests, add retry logic

Risk: Team doesn't understand testing infrastructure
  → Mitigation: Comprehensive documentation + training
